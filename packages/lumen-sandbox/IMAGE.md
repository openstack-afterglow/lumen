# Sandbox image contract (0.1.1)

The `lumen-sandbox` target in `docker/Dockerfile` supports linux/amd64 and linux/arm64. It contains only the `lumen-sandbox` wheel and its declared Python dependencies, the pinned Node runtime, and the tools described below (no `lumen`, `lumen-plugin-api`, service credentials, Docker socket or host mounts). Both daemon entry points refuse non-Linux hosts. The default command remains the root-managed standalone daemon; the Kubernetes provider explicitly overrides it.

## Kubernetes image and tool contract

The Kubernetes provider runs `lumen-sandbox-kubernetes` as uid/gid **4300:4300**, with `readOnlyRootFilesystem`, all capabilities dropped, and no privilege escalation. `/work` is the per-run, bounded `emptyDir` tmpfs; `HOME=/work` and `TMPDIR=/work/tmp`. Writable daemon state is mounted separately at `/state`. The provider supplies `SANDBOX_STATE_DIR=/state`, `SANDBOX_WORKSPACE_DIR=/work`, `SANDBOX_TOOL_MANIFEST=/opt/lumen-tools/manifest.json`, its SHA-256 in `SANDBOX_TOOL_MANIFEST_SHA256`, and the bootstrap/resource/limit configuration required by `kubernetes_server.py`. The image's root-manager defaults below apply only to the standalone entry point, not to this Kubernetes override. No tool downloads or package installation occur at runtime.

MCP's exact Playwright dependency is **1.64.0-alpha-1790635538000**, with Chromium revision **1247**, browser version **155.0.8059.12**. That lockfile's Playwright CLI installs its matching Chromium and OS dependencies at build time, using `install --with-deps --no-shell chromium` for each target architecture. `/opt/ms-playwright/chromium` points to that bundled executable, not a separately installed Google Chrome channel.
- `/opt/lumen-tools` and `/opt/ms-playwright` are root-owned, world-readable/searchable, and not writable by the workload. All profile commands use absolute node/script paths.

Playwright is headless and isolated (in-memory browser profile), with artifacts under `/work`. Its committed JSON config explicitly selects the bundled Chromium executable; `--browser chromium` alone is not used to select a Chrome channel. **Chromium's own sandbox defaults ON** (`browser.launchOptions.chromiumSandbox=true`). The parent/operator **must confirm real browser navigation and snapshot behavior on the target gVisor runtime** before promotion; local Docker results do not qualify gVisor. If measurement requires disabling the Chromium sandbox inside the outer sandbox, build and approve a distinct image with `--build-arg PLAYWRIGHT_CHROMIUM_SANDBOX=false`; Playwright then supplies Chromium's `--no-sandbox`. Only literal `true` and `false` are accepted. This is an image-build parameter, not a caller-controlled MCP argument or an automatic fallback. Pin the chosen image digest and review its config as well as its manifest. Disabling Chromium's sandbox weakens defense in depth.

The version-1 manifest defines `playwright` and `filesystem`. The filesystem server receives only `/work` as its allowed root. Approved tool names, descriptions and exact `tools/list` input schemas are committed in `tools/manifest.json`; changes to dependency versions require recollecting those schemas from the actual pinned servers. Effects use core's `read`, `workspace_write`, `process`, and `external_mutation` vocabulary. Read-only operations are `read`; filesystem mutations are `workspace_write`; browser interactions that may mutate a remote site are `external_mutation`. `browser_run_code_unsafe`, `browser_evaluate`, and `browser_file_upload` are never approved. MCP startup requires every approved tool to be advertised, but ignores additional advertised tools; HTTP dispatch rejects any tool not approved by the manifest with `400 unapproved_tool`.

| --- | --- |
| `playwright` / `workspace_write` | `browser_console_messages`, `browser_find`, `browser_network_requests`, `browser_network_request`, `browser_take_screenshot`, `browser_snapshot`, `browser_wait_for` |

Browser observer tools are conservatively `workspace_write`, not `read`: this pinned version can persist their output artifacts, including the implicit snapshot produced by `browser_wait_for`. Only operations that cannot mutate workspace or remote state are marked `read`. The authoritative effect Literal is `lumen_plugin_api.tools.ToolDefinition`; `lumen/services/tool_runtime/contracts.py` uses the same four-value set.

### Extracting the operator manifest

Extract the exact bytes from the **approved image digest**, not from a mutable tag or a reformatted JSON copy. For example, from the repository root:

```bash
IMAGE='registry.example/lumen-sandbox@sha256:REPLACE_WITH_APPROVED_DIGEST'
container=$(docker create "$IMAGE")
docker cp "$container:/opt/lumen-tools/manifest.json" ./lumen-tools-manifest.json
docker cp "$container:/opt/lumen-tools/playwright.config.json" ./lumen-playwright-config.json
docker rm "$container"
shasum -a 256 ./lumen-tools-manifest.json
```

Set the Kubernetes profile's `tool_manifest_file` to the absolute controller-side path of `lumen-tools-manifest.json` and `tool_manifest_sha256` to the printed 64-character lowercase hash. Set the sandbox image reference to the same immutable digest. The provider passes the hash to the pod, which validates the baked manifest bytes before starting. The manifest hash covers the allow-list; the image digest additionally binds browser config, dependencies, and executable bytes. Multi-architecture images must carry identical manifest bytes, and each platform must be qualified independently.

### Kubernetes tool qualification

Build the canonical targets (from the repository root):

```bash
docker buildx build --platform linux/arm64 -f docker/Dockerfile --target lumen-sandbox --load -t lumen-sandbox:k8s-arm64 .
docker buildx build --platform linux/amd64 -f docker/Dockerfile --target lumen-sandbox --load -t lumen-sandbox:k8s-amd64 .
```

For each image, run both manifest commands as real stdio MCP sessions with `--user 4300:4300 --read-only --cap-drop ALL --security-opt no-new-privileges --tmpfs /work:uid=4300,gid=4300,mode=0700`, and `HOME=/work`, `TMPDIR=/work/tmp`. Send `initialize`, `notifications/initialized`, and `tools/list`; compare every approved schema. On native arm64 additionally call `browser_navigate` for `https://example.com`, `browser_snapshot`, and filesystem write/read inside `/work`. Record image IDs, sizes, manifest hashes, and exact results. A failed browser launch is a failed qualification, never a reason to silently disable the sandbox. Confirm the selected sandbox mode separately under live gVisor. Run package pytest and ruff after image/runtime qualification.

Local Docker Desktop qualification built both canonical architectures and exercised both profiles with the restrictions above. All 22 approved Playwright and 14 filesystem schemas/descriptions matched the real servers; filesystem write/read passed on both architectures. Node reported `v24.21.0` with `arm64`/`x64` respectively, and Chromium reported `Google Chrome for Testing 155.0.8059.12`. The native arm64 **default sandbox-ON** browser calls failed with `No usable sandbox!`: under these restrictions `unshare(CLONE_NEWUSER)` returned `EPERM`, with `NoNewPrivs=1`, seccomp filtering enabled, and no effective capabilities. A separately tagged arm64 image built with `PLAYWRIGHT_CHROMIUM_SANDBOX=false` passed real `https://example.com` navigation (title `Example Domain`), snapshot, and filesystem write/read under the same outer restrictions. This proves the opt-in packaging path only; the default browser and target-gVisor acceptance remain unqualified. No automatic downgrade was introduced.

## Required image and host

- Python **3.12** at `/usr/bin/python3.12`, an exact pinned Node LTS release (version **and** per-architecture checksum/digest, not a floating `lts` tag) at `/usr/bin/node` (`SANDBOX_NODE_MAJOR` must equal the installed major), `/bin/sh`, bubblewrap at `/usr/bin/bwrap`, mount/umount at `/usr/bin/{mount,umount}`, nft at `/usr/sbin/nft`; keep their loader/libraries under read-only `/usr`, `/bin`, `/lib`, `/lib64` (the only interpreter bind mounts). Include CA roots for bootstrap manager only. No writable package installation at runtime.
- Root manager only, with distinct nonzero `SANDBOX_WORKLOAD_UID` and `SANDBOX_WORKLOAD_GID` (not a login/shared service identity), user/PID/mount/network namespace creation permitted, `no_new_privs`, and writable *dedicated* cgroup v2 parent with `cpu memory pids` controllers delegated. Child limits `memory.max`, `memory.swap.max=0`, `pids.max`, `cpu.max`; `workspace_bytes <= memory_bytes/4`. Image/runtime must allow manager mount of `tmpfs` and bubblewrap's unprivileged user namespace. Root-owned daemon state and bootstrap/certificate material must not reside under any workload bind mount. Workload has one bounded host tmpfs at `/work` inside the net/mount/user/PID namespaces (`HOME` and `TMPDIR` both point there), no UP non-loopback network interface, no inherited credentials or environment, no other writable filesystem except the isolated `/dev` device nodes. The daemon is not a general shared multi-tenant host: one run, one allocation, no replacement run on the same state directory.
- Set `SANDBOX_STATE_DIR`, `SANDBOX_WORKSPACE_DIR`, `SANDBOX_CGROUP_PARENT`, `SANDBOX_WORKLOAD_UID`, `SANDBOX_WORKLOAD_GID`, `SANDBOX_MEMORY_BYTES`, `SANDBOX_WORKSPACE_BYTES`, `SANDBOX_CPU_QUOTA` (microseconds per 100000), `SANDBOX_PIDS_LIMIT`, `SANDBOX_NODE_MAJOR`, `SANDBOX_NODE_VERSION` (exact numeric version, e.g. `24.13.0`, verified against `node --version`), `SANDBOX_BOOTSTRAP_FILE`, `SANDBOX_CONTROLLER_URL` (HTTPS), `SANDBOX_CONTROLLER_CA` (pinned CA file); optional `SANDBOX_PORT` (8013), `SANDBOX_HOST`. State dir and bootstrap parent must be root-owned mode 0700 and non-workload-visible; one-shot file must be root-owned 0600 regular file, one link, no symlink. `SANDBOX_WORKSPACE_DIR` must be a unique mountpoint outside state, under a root-owned searchable parent (0711 recommended), accessible to the workload UID after tmpfs mount. Persist SQLite state *and the mounted workspace tmpfs* across manager restarts of the same generation; the resource owner unmounts and deletes the workspace only on permanent allocation teardown. Do not copy state or reuse workspace across runs.
- The guest host firewall must create an `inet lumen_sandbox output` base chain at output hook with policy **drop**. During bootstrap only, allow the manager to reach the dedicated controller bootstrap listener (pin its destination IP and TCP port; disallow general DNS/proxy/registry access at runtime). Manager exchanges token over CA-verified HTTPS, scrubs/unlinks token and flushes this chain, installing solely `ct state established,related accept` before serving. Deny new outbound flows to metadata `169.254.169.254` and `fd00:ec2::254`, loopback, daemon port, API/DB/Redis/Keystone/controller/other guests/Internet on IPv4 and IPv6. Input chain permits only the configured mTLS daemon port from managed worker/controller subnets and established replies. The workload netns has no usable external interface (no UP non-loopback interface or proxy); kernel-created inert tunnel devices may exist DOWN. The workload drops all capabilities and cannot enable them, so metadata/daemon cannot be reached from code. Configure Neutron security groups to permit boot-only bootstrap, then close it before accepting work. `preflight.verify` checks image, Linux/root, bounds, cgroups; `activate_runtime_firewall` verifies drop after transition. A firewall policy file without effective guest rules is not sufficient.

`cgroup.controllers` only lists *available* controllers. The dedicated `SANDBOX_CGROUP_PARENT/cgroup.subtree_control` must actually contain `cpu memory pids` before the daemon starts; otherwise child `memory.max`, `pids.max`, and `cpu.max` are not enforceable, and startup fails before mounting the workspace. The host must move the manager into a sibling/leaf cgroup before enabling controllers on its parent (cgroup v2's no-internal-process rule). The daemon does not enable missing host controllers itself or silently run without limits.

Before mTLS serves, `verify_workload_network` actually starts the fixed Python probe inside the bwrap namespace: every non-loopback interface visible in `/proc/net/dev` must be administratively DOWN (kernel-created inert tunnels are allowed); attempted connections to IPv4/IPv6 metadata, 127.0.0.1/::1 daemon port and a public IPv4 address must all fail. This is in addition to the default-drop nft check, not a substitute for the runtime security-group policy.

If the journal survives but the tmpfs mount does not, the daemon refuses to resume: revision fencing cannot authorize another call in an empty workspace. Controller must mark the allocation's result uncertain and replace the resource rather than resetting or replaying it.

## Disposable local isolation acceptance

On a trusted, disposable Linux Docker host with cgroup v2 and namespace support, run both image architectures. `--privileged` here is for a **test-only** private container cgroup namespace; do not use it as the production sandbox deployment policy. The bind mount contains only the test sources. Installing pytest/httpx inside this temporary test container does not change the built image.

```bash
for arch in amd64 arm64; do
  docker buildx build --platform "linux/$arch" -f docker/Dockerfile --target lumen-sandbox --tag "lumen-sandbox:local-$arch" --load .
  docker run --rm --privileged --cgroupns=private --platform "linux/$arch" \
    --entrypoint /bin/sh --mount type=bind,src="$PWD/packages/lumen-sandbox/tests",dst=/tests,readonly \
    "lumen-sandbox:local-$arch" -c 'set -eu; mkdir /sys/fs/cgroup/lumen-manager; echo $$ > /sys/fs/cgroup/lumen-manager/cgroup.procs; echo +cpu +memory +pids > /sys/fs/cgroup/cgroup.subtree_control; python -m pip install --quiet pytest httpx; python -m pytest -q -p no:cacheprovider /tests'
done
```

The manager runs in `lumen-manager` while the sandbox creates separately limited child cgroups under the parent. The real workload tests exercise namespace network denial, bounded tmpfs, CPU/PID/memory setup, memory OOM, cancellation and Python/Node/shell execution; the failure regression checks that absent delegation does not leave a workspace mount. This test does **not** prove Nova/Zun/KVM security groups, controller TLS, or production host policy.

Each architecture must pass the real workload cases on a host that implements bubblewrap namespace/mount syscalls for that architecture. On this arm64 workstation, the arm64 container passed all 21 tests, while amd64 emulation passed 14 non-workload contracts but `bwrap --unshare-all --ro-bind /usr /usr` failed with `Function not implemented`; that is **not** an amd64 isolation pass. Re-run the complete suite on native linux/amd64 before approving that image for deployment.


## Bootstrap and TLS

`POST {SANDBOX_CONTROLLER_URL}/v1/sandbox/bootstrap` JSON `{"token":"...","csr_pem":"..."}` with TLS validated by `SANDBOX_CONTROLLER_CA`. Controller atomically consumes token and returns JSON `resource_id`, `run_id`, `generation` (integer), `image_id`, `policy_id`, `certificate_pem` (certificate for CSR's generated P-256 private key), `client_ca_pem` (trusted worker/controller client CA), `dispatch_key` (base64url random >=32 bytes). The daemon generates its private key locally, writes key/cert/client CA as root-only 0600 under daemon state; serve HTTPS with client certificate **required**, no HTTP listener or reverse-proxy header trust. Controller and worker must verify server cert and resource generation identity. Failed bootstrap fails closed, with no workload execution.

Bootstrap response also **requires** `run_deadline` (Unix seconds from the resource row's immutable root policy). New POSTs at/after this deadline return 409 while matching existing calls still replay; an in-flight timeout is capped to remaining wall time and the process group is killed at deadline. `/readyz` returns 503 when expired; status, cancel and artifact reads remain available for reconciliation.

## HTTP and capability contract

Every dispatch/status/cancel/artifact request requires both mTLS client cert and `Authorization: Bearer <payload64>.<mac64>`. `payload64=base64url_no_padding(UTF-8 JSON sorted keys, compact separators, ensure_ascii=False)`, `mac64=base64url_no_padding(HMAC-SHA256(dispatch_key, raw_payload_bytes))`; binary HMAC compare is constant-time. Payload object: `{"aud":"lumen-sandbox","resource_id":"...","run_id":"...","generation":N,"method":"POST|GET|DELETE","path":"/v1/executions...", "fence":N,"exp":UNIX_SECONDS}` (numeric expiration strictly in the future and no later than server now+15 seconds). POST additionally includes `call_id`, `workspace_revision`, and `fingerprint`: lowercase SHA-256 hex of the *validated entire JSON request object* serialized using that same canonical JSON encoding. POST request fields exactly `run_id`, `call_id`, `fence`, `language` (`python|javascript|shell`), `source`, `timeout_seconds` (positive <=300), `workspace_revision` (nonnegative integer). Signed path is exact URL path including execution/artifact UUID, never a wildcard. Controller signs only after run/approval/resource-generation/fence/cancellation checks. All other fields in the signed object are ignored (never grant privileges); use unique per-resource-generation key. GET `/readyz` has no bearer but requires mTLS and returns resource/run/generation/image/policy identity and language/limit metadata, never credentials.

The reference implementation for signer and verifier is `lumen_sandbox.envelope.sign(payload, key)` and `verify(header, key, now=...)`; `sign` returns the complete `Bearer ...` header value. The signer requires the controller to supply the fields above and signs the canonical payload without injecting any defaults. The verifier authenticates canonical bytes and the 15-second expiry; each server route additionally checks its own audience, generation, run, exact path/method, fence and request fingerprint.

POST returns 202 with stable `{id,call_id,fence,workspace_revision,state}` immediately after SQLite FULL-sync reservation, replay 200 with previous status, conflicting call ID or stale fence/revision/active call 409. GET returns state, bounded decoded stdout/stderr, exit code, duration, artifact refs after terminal completion; `indeterminate` means identity was durable but outcome was lost on restart and neither it nor a later call is run in that workspace. DELETE waits for whole cgroup/process-group cancellation and returns terminal state (or existing terminal state idempotently). Artifact GET streams only a frozen, daemon-owned snapshot after child termination, maximum 20 regular files, each <=5 MiB; no arbitrary paths/symlinks. Worker performs scan and authoritative asset ingest before deletion. Snapshot errors fail the execution explicitly. States: `reserved`, `running`, `succeeded`, `failed`, `cancelled`, `timed_out`, `output_limit_exceeded`, `indeterminate`. Terminal calls advance workspace revision exactly once; next POST supplies the new revision.
