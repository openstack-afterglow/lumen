# Lumen Architecture

## Overview

Lumen은 owned provider transport(`provider_client` + private Bifrost converter), LangGraph/LangChain agent runtime, 대화·durable run journal, server-managed tool/skill/memory, usage ledger와 provider secret을 소유하는 독립 AI 채팅 서비스다. Afterglow는 제품 UI와 인증된 BFF를 소유하고, Lumen은 `/v1` API와 실제 실행·영속성을 소유한다.

- Repository: https://github.com/openstack-afterglow/lumen
- 분석 기준: `dev` branch, 현재 working tree source와 설정
- 버전: root candidate `lumen` `0.6.11` extends published `0.6.10` dev `c27e540` with optional Valkey Sentinel routing and owned cache-pool cleanup. Fresh local qualification is recorded in `docs/testing.md`, not artifact publication or production change. Plugin API/default plugins remain `0.1.1`, database plugin `0.1.2`, independent SDK `0.2.1`, and discovery/API contract `1.0.0`; Kubernetes/tool-manifest and owner/credential fences remain. Published Kubernetes027 and any exact historical account027 receipt are immutable. Forward028 reconciles only supported inspected states without rewriting/replaying applied SQL/checksums. All writers must drain/stop and protected matching-engine restore/migration/rerun must pass before cutover.
- 주요 실행 단위: FastAPI API(`lumen/main.py`), durable worker(`lumen/worker.py`), migration CLI(`lumen/scripts/migrate.py`), migration 이후 provider bootstrap CLI(`lumen/scripts/seed_providers.py`), 독립 `lumen-sdk`, 선택적 local Console(`lumen_console/`)

짧게 말하면 대부분의 HTTP route는 인증·scope·입력 검증과 journal 조회만 담당하고, `chat_admission`이 실행에 필요한 권한·context·provider/model·extension snapshot을 고정한다. `durable_runs`가 MariaDB transaction으로 intent/run/event를 기록하고, worker가 lease를 획득해 provider·tool을 실행한다. Redis는 일반 run wakeup 최적화지만 realtime 한 번 쓰는 connect ticket에는 필수다. Realtime 예외는 API WebSocket process가 직접 lease를 소유하며 양방향 provider audio를 relay/정산한다.

### 0.6.11 Valkey Sentinel routing

The cache singleton in `lumen/cache.py` remains synchronous to construct and async to use: existing `_get_client`, `_get_redis`, cache, queue, realtime ticket and controller callers keep one convention. Optional `redis_sentinel_addresses`/`redis_sentinel_master` select the current primary through Sentinel; URL hostname/port never bypass discovery. `redis_url` and the locked redis-py5.0.0 client retain their wire-compatible names; the actual server product is Valkey. URL data username/password/database/options remain data-node properties, with separate SecretStr `redis_sentinel_password` and optional ACL `redis_sentinel_username` for discovery. Rediss TLS and URI socket/TLS options reach both discovery and managed data pools. Bounded coherent settings reject invalid topology, connection-class overrides and nonfinite/unbounded socket timeouts before use.

Sentinel mode alone sets zero command retries: lost replies and old-primary READONLY failures surface to the consumer, and only a later independent operation reconnects/discovers the new primary. No seed/replica/proxy fallback is added. Construction performs no network I/O/await; API, worker and controller own all discovery/data pools and clear the singleton before attempting every close, surfacing cleanup failures. Kolla renders Valkey inventory, `valkey_sentinel_port`/monitor name and the separate optional `valkey_sentinel_password` into the protected config and every service/bootstrap environment. Direct mode retains its existing URL precedence/timeouts/health checks. Root/runtime/image default is0.6.11; SDK/plugin/sandbox versions and all027/028 schema/manifest bytes remain unchanged. Local/native/publication/rollout evidence are separate in `docs/testing.md`.

### 0.6.10 provider cutover (locally qualified, not deployed, 2026-10-26)

`provider_client.py` owns request/stream lifetime and sanitized `provider_errors.py` exceptions; `provider_metadata.py` owns offline catalog, token estimates and frozen pricing. `bifrost_runtime.py` owns one authenticated loopback child per API/worker process. `runtime/bifrost/` pins Apache-2.0 Bifrost core `v1.13.2-0.20261021235121-668a660e5ac0` (Go 1.27.3, `go.sum`, LICENSE/NOTICE). It uses upstream request/response converters with Lumen-owned HTTP execution, not stock Bifrost gateway routing, key selection, budgets, caching, governance or retry orchestration. Public API and customer authorization remain Python-owned. The dated receipts below describe their original source revision; LiteLLM-era passes are not acceptance of this cutover.

Endpoint → account → credential is a private ownership hierarchy, not a cross-endpoint pool. Admission selects once using endpoint `explicit`, `priority` or `weighted` policy; priority sorts account priority, credential priority and IDs, while weighted selection uses account weight × credential weight. A secret-free `ProviderAuthRef` freezes provider/account/credential IDs, generation, auth mode, model ID and required operations. At every new I/O, current enabled state, expiry/cooldown, model/operation eligibility, ownership and generation are checked against that exact reference. A failed check never selects another account. `allowed_capabilities` are operation tags (`chat`, `responses`, `messages`, `count_tokens`, `embeddings`, `search`, `image`, `tts`, `stt`, `realtime`), not inferred model features; `null` is unrestricted and `[]` denies all. Allowed model IDs must belong to the endpoint.

There is no same-request retry, shadow, fallback, credential rotation or engine switch after admission. Python resolves only the selected request-local secret; the converter performs at most one upstream send, rejects `single_attempt=false`, does not follow redirects and requires genuine stream terminals. Native Responses and Anthropic Messages/count_tokens retain native schemas where conversion would lose fidelity; converted chat/embedding paths use pinned Bifrost converters. Official direct OpenAI chat-shaped requests use Responses, custom OpenAI-compatible bases retain Chat Completions. Python owns public error mapping, durable provider-start/checkpoint/unknown classification and settlement. Ambiguous disconnects/truncation preserve unknown holds rather than replaying inference.

Backend provenance is explicit: text converter `bifrost` plus pinned core version; direct media `lumen-media-direct:1`, search `lumen-search-http:1`, ChatGPT/Codex subscription `lumen-codex-http:1`. Direct paths share the exact selected credential/current-authority boundary and do not masquerade as Bifrost execution. ChatGPT explicit output caps/sampling are rejected before I/O; only implicit service defaults are omitted under frozen intent, and bounded Batch/agent use is excluded. Subscription protocol support is not provider permission for public multi-user pooling.

Forward migration028 owns account/credential schema and compatibility reconciliation; published Kubernetes027 and the historical account027 receipt remain immutable. Existing endpoint credentials move only through validated supported-state reconciliation to account credentials, preserving ciphertext/env references/generation, separate billing keys and all durable journals. Account allocations commit atomically with the one customer debit; historical usage remains unattributed. Credential probes are explicit bounded exact-key operations. Settled `/relays` history projects actual transport receipts stored with usage, never current endpoint configuration or reconstructed historical destinations. See [operations](docs/operations.md#private-provider-runtime-and-migration028-cutover) and the [candidate gate list](docs/testing.md#0610-integrated-candidate-required-gates); historical receipts below do not qualify this tree.

Fresh local qualification: service4,737/SDK143, plugins97+1skip, sandbox33+21skips, Kolla100, complete MariaDB integration445 on canonical11.x and actual10.11.19/live strict utf8mb3 defaults, canonical system31 each arm64/emulated-amd64, eight image executions and pinned Go test/vet passed. Real Uvicorn/worker/SQL/Redis account fixtures passed76 assertions; encrypted PostgreSQL protocol-v2 passed164 with same-thread SDK continuation,16 checkpoints/82 encrypted blobs, exact selected sends and single-debit allocation. [Testing](docs/testing.md#fresh-local-qualification-2026-10-26) records source/image bindings, retained failures and unexercised boundaries. MCP 호출은 authenticated workspace revision을 조회하여 서로 다른 도구·새 approval worker가 동일 journal revision을 사용하며, media 결과는 generated tool file로 전달한다. 자동 approval 만료는 frozen dispatch 검증 후 서명된 deny로 재개한다. 이 불변식의 최종 native/production 증거는 아직 pending이다.

Ingress enable/create holds the pool lease row lock until the actual SDK thread settles, including cancellation, and renews the locked lease while waiting. Durable one-shot ingress intent survives response loss/restart; reconciliation adopts only exact resource/generation tags plus name/address/port/subnet identity. A known or just-observed member ID stays pinned through adoption/re-enable and requires a direct SDK read; disappearance cannot cause an unclaimed new create. A not-ACTIVE pool may defer a create intent only when no member write was submitted, under the same owner/fence with attempts=0. Submitted ambiguous creates retain quota and are never blindly resubmitted. Unavailable API guests with a recorded member can enter fenced drain, but VM deletion still requires applied weight zero, fresh zero counters/current-fence acknowledgment and confirmed member removal. Live cloud rollout remains unverified.

## Runtime flows

### Current service authority and evidence

Authorization binds exact unique global role IDs from fresh effective Keystone project assignments; it does not reconstruct service leaf roles. `lumen/policy.py` registers scope-named action `RuleDefault`s with the real oslo.policy Enforcer and a service-local ConfigOpts. Each action explicitly accepts the relevant `lumen_admin/editor/user/reader` grades, its exact explicit leaf grant, current project `admin`, and verified system administrator by default. No native member/reader co-role or service implication edges are needed; bare manager/member/reader/project_owner/project_admin or another service's administrator remain unentitled. The inference DAG remains validated for native integrity and raw direct/group human system administration, not as the service permission hierarchy. Disabled/deleted native identity is 403; incomplete/malformed/unavailable identity/catalog/assignment state is 503. Domain aliases never become trusted global roles. Owner/API-key/pre-I/O consumers use this same uncached native resolver.

Verified personal membership is a separate project-only default alternative: fresh native project `afterglow_personal_user_id` must equal the actual user, its enabled owning domain must have exact native name `Personal` (kind absent or `personal`), and the enabled user/home/project/domain must be current. A complete raw project grant inventory must contain only that user's direct global `member`; effective rows must retain direct provenance and only member/reader, with no group/inherited/foreign authority or member-to-admin/service inference. This derives an internal `personal_project_owner` policy credential, never roles or a BFF claim. Original unrestricted human project scope is required at HTTP refresh; reduced credentials and logical foreign/rescoped targets do not gain it. API-key owner and worker/new-I/O resolution recompute it while preserving stored action ceilings. `system:admin`, global provider/settings/templates, ownership and provider/grant restrictions remain unchanged; explicit operator YAML deny still wins. Personal regressions are test-defined only in this change; no checks or deployment ran.

Because oslo.policy RoleCheck is case-insensitive, the native catalog rejects distinct global role IDs with casefold-equivalent names before policy evaluation (including operator custom roles); builtin domain/global collisions are also casefold-aware. Returned role names remain actual native spellings, never normalized aliases.

Malformed policy YAML/documents/references surface as HTTP 503 and recover on corrected native reload; ordinary policy rejection is 403. Local seed binds the verified owner user/project onto the resolver's ID-less authority result before the same policy is evaluated for issuance and rotation.

All authority collections use raw installed-client HTTP envelopes before SDK managers discard pagination metadata: `/roles`, `/role_inferences`, user group membership and raw/effective assignment collections require a dictionary envelope, all-dictionary rows, dictionary links with no `next` and no `truncated` marker. Partial/malformed collections are 503, not positive or negative authority; system queries encode exact `user.id`/`group.id` and `scope.system=all` without an effective/admin-role prefilter.

Operator policy uses TOML `[oslo_policy] policy_file="/etc/lumen/policy.yaml"`, `policy_dirs=[]` and corresponding `OSLO_POLICY_POLICY_FILE`/JSON `OSLO_POLICY_POLICY_DIRS` environment overrides. Absent policy files select registered defaults. Native file/directory reload applies changes at the next authorization; invalid YAML shapes, malformed checks, undefined/cyclic rules deny rather than reusing a prior allow. `oslo.policy.policies` and `oslo.policy.enforcer` expose namespace `lumen`; the packaged sample is `lumen/policy.yaml.sample`. Authenticated `GET /v1/policy/capabilities` has no entitlement prerequisite and returns deterministic `{service,capabilities,actions}` from actual policy plus key ceilings. Capability names are UI projections of singleton action families, never fabricated token roles or secondary gates. Implementation and regression definitions are unverified in this assignment; no runtime/deployment result is claimed.

Issuance requires `native:keys:write` and every requested action under current owner and authenticated caller policy; use does not require retaining the issuance action. API/compat admission, dynamic media/tools/agent/search checks, durable workers and auxiliary generation use the same policy and stored-key attenuation before **new I/O**. User/project ownership, enabled identity, key active/revoke/expiry/owner/scope, quota, MCP consent and provider prerequisites remain independent even if a YAML action is `@`. Completed checkpoints and committed provider-start recovery/settlement are not reauthorized or re-invoked. Cancellation first loads ownership and checks only the operation's primary generation action.

Provider stream open/consume 실패는 `provider_failed` boundary 뒤 중단하고 같은 요청을 다른 effort/default/key/engine으로 재호출하지 않는다. 새 admission을 위한 reasoning 오류 학습·memo를 유지한다고 가정하지 않는다. 과거 hookless retry 설명은 current single-attempt cutover에 적용하지 않으며 child도 같은 단일 호출 전달 경로를 사용한다.

**Historical 0.3.1 implementation, no longer current:** 당시 세 reasoning memo (`_REASONING_UNSUPPORTED`, `_TOOL_REASONING_EXPLICIT_NONE`, `_TOOL_REASONING_NONE_REJECTED`)의 key는 model 이름 대신 worker의 `config_version_hash`였고 `reasoning_route_key`를 execution→engine→graph로 전달했다. Frozen identity가 없는 호출은 memo를 재사용하지 않고 명시 none을 stale probe/default retry로 바꾸지 않는 회귀를 정의했다. 이 memo·route-key 전달·암묵 GPT-5 none 주입은 현재 converter cutover의 graph/engine/execution/provider_client 실행 기제가 아니며 새로운 admission을 구동하지 않는다. 아래0.4.0 test receipt는 이 과거 source에 관한 기록이다.

Opaque OpenAI route의 명시 `none`은 owned provider request에서 보존하고 오류 뒤 provider-default reasoning으로 바꾸어 재시도하지 않는다. 과거 `drop_params`/`allowed_openai_params`/`get_optional_params` mapper 검증은 제거된 LiteLLM 경계의 역사적 회귀이며 현재 source는 `provider_client`와 pinned converter를 사용한다.

0.4.0 후보에서 0.3.1 reasoning 수정과 media 경로를 합친 뒤 contract 1,448건·SDK 125건, 실제 MariaDB/Redis integration 43건, containerized API/worker system 9건을 통과했다. `lumen-api`, `lumen-worker`, `lumen-controller`, `lumen-sandbox` 각각 linux/amd64·linux/arm64 이미지를 빌드하고 두 플랫폼에서 실제 실행해 Python machine/version 및 sandbox Node v24.21.0을 확인했다. 이는 local build/runtime 증거이며 GHCR tag 게시·Kolla migration/배포 증거는 아니다.

### Plugin selection, managed resources and child joins

`lumen-plugin-api`는 실행 DTO/Protocol만 게시한다. 관리자 allowlist의 distribution/name/version이 실제 entry point와 일치해야 registry가 시작되고, host는 필요한 capability만 플러그인에 전달한다. Nova create의 lost response는 unknown intent로 유지해 중복 생성·임의 삭제를 금지한다. Zun은 adapter 코드가 있지만 sandbox host isolation 강제가 없어서 pool config가 모든 Zun 역할을 거부한다. 외부 OpenStack 제공자의 안전성/격리는 cloud 검증 전까지 입증되지 않는다.

### Active-path history and branches

`chat_message_graphs(id,user_id,project_id)` owns encrypted immutable message bodies; `chat_conversations.graph_id` is an independently titled mapping with a selected leaf, `history_revision` and `chat_conversation_active_path(conversation_id,position,message_id)`. `chat_messages.graph_id` fixes ownership; `conversation_id` is nullable creation provenance only. `chat_conversation_messages` explicitly grants reachability to a conversation, including inherited ancestor IDs; a shared graph alone does not authorize a sibling branch. Writers and readers require conversation user/project plus graph owner, matching message graph and membership; changing an ancestor shared with a fork is refused. Fork creates mapping/membership/projection rows without copying message bodies, ciphertext or asset links; source deletion does not break a fork, and the final mapping deletion atomically removes graph, messages and message-asset links. Origin run/usage audit follows its existing retention/SET NULL rules.

`lumen-migrate --apply` applies additive migration 019 to each legacy conversation as its own graph; already copied forks are never content-deduplicated. It discovers the actual old origin FK name/collation, backfills graph IDs and all legacy origin memberships, checks owner/graph integrity before NOT NULL/FK/index DDL, projects any unready histories, and verifies contiguous/root-to-leaf/terminal/membership paths before recording the migration ledger. Partial DDL is resumable and a second application is inert. Stop writers, back up MariaDB and coordinate API/worker cutover; a mixed old/new deployment is unsafe.

The hot page path reads indexed active-path positions from the selected leaf backwards for `anchor=latest` or an exclusive before cursor, then reverses the bounded page into display order. A revision mismatch returns 409; malformed or cross-conversation opaque cursors return 422. `ChatMessage.conversation_id` is never used to authorize inherited messages, and `_msg_public` reports the requested view conversation. Inherited user messages cannot expose the source run as fork-local retry; title jobs snapshot the reachable first exchange under the selected conversation lock, with manual title revision CAS fencing later results.

### Worker recovery and background work

`lumen/worker.py`는 `worker_workload_classes`로 registration을 만들고 capacity만큼 active task를 유지하면서 빈 slot을 즉시 채운다. 기본 fixed worker는 `online_text`/`online_media`, batch worker는 단독 `batch` class다. 모든 worker는 stale run recovery를 수행하되 자기 registration이 claim할 수 있는 run만 launch한다. Pending input/approval expiry, temporary thread purge, title/memory/outbox/background workspace jobs는 online_text worker에서만 registration UUID owner로 실행한다. Managed worker 등록은 bootstrap-issued generation/certificate fingerprint, plugin digest와 pool class를 DB에 고정한다. 새 claim은 현재 resource readiness·protocol·plugin digest·20초 이내 heartbeat·accepting·live lease capacity를 검증한다. SIGTERM은 durable drain fence를 먼저 commit해 run/auxiliary 새 claim을 막는다. 기존 run과 이미 admitted auxiliary step은 cancel하지 않고 완료한다. Live run/auxiliary lease가 0이 된 뒤에만 drain ack를 기록하고 종료한다. API guest의 독립 mTLS `/v1/ready`는 public process의 DB/plugin/checkpointer와 loopback-only active/SSE count·streaming 첫 text p95를 보고한다. Controller는 probe 실패 시 ingress를 disable하고 freshness 없는 telemetry로 scale-down하지 않는다. Redis wakeup은 최적화이고 MariaDB queued state·lease·journal이 복구 기준이다.

Title recovery reuses the durable first-title job rather than doing model work in a GET. Once per idle minute it selects an active, titleless `auto/idle/revision=0` conversation with a completed persistent root exchange and no title job; empty conversations cannot starve later candidates. The selected mapping's reachable first user/assistant exchange (including inherited user IDs) is snapshotted into its title job under its lock. Unusable route/source candidates become `unavailable`. Manual updates atomically mark the title explicit/ready and advance its revision; late title results fail the revision CAS. Legacy/manual/failed/deleted rows and ambiguous provider calls are not replayed.

The title call (`lumen/services/title_summary.py`) sends a reasoning effort only when the frozen route's `capabilities.reasoning_options` advertises an `effort` list. It picks the cheapest listed value in the order `none → minimal → low → medium → high → xhigh → max`, so gpt-5 gets `minimal`, o3 gets `low`, gpt-5.1 gets `none`, and claude-opus-5-5 gets `low`. Routes with only `budget_tokens`/`toggle` options, empty options (LiteLLM/ChatGPT fallback capabilities), `reasoning=false`, or no capabilities omit the effort and keep the provider default. `_reasoning_params` preserves advertised `none` even when the provider catalogue probe is stale; other chosen efforts still require the provider probe. Options enter the real `acompletion` wrapper through `extra`, not unsupported top-level keywords. Integrated-tree contract 1,369 and MariaDB integration 70 passed (2026-09-27), including fork first-title snapshot and manual revision fence; this does not prove a live title-model response, storage on production, or sidebar rendering against production. No service, store, or ownership boundary is added by the title parameter change.

Context capacity resolves exact catalog input windows, including the stored Perplexity route alias, while explicit reviewed overrides retain precedence. Unknown limits, uncountable input and invalid budgets have distinct reason codes and never project a fabricated percentage. Text counter failure retains a labeled estimate. Both manual compaction endpoints return the actual unavailable reason. Agent search-result events/output items (including `response.output_item.added`) survive LiteLLM's empty-chunk filtering through provider-specific delta metadata, then join URL annotations in the canonical citation projection without losing inline ranges. A failed tool-schema validation is persisted and emitted with failed tool status rather than being projected as a completed task. These changes add no service, database schema or ownership boundary.

Provider-native compaction layers under, not over, that fence. `native_compaction.py` resolves an Anthropic `context_management` edit at the same 0.80 occupancy ratio, but the provider trigger is an absolute input-token count against the raw window while the Lumen fence divides by `input_budget`, so the Lumen fence always trips first and stays the durable, provider-neutral mechanism. The edit is armed only where the pinned LiteLLM chat transport forwards `context_management` — Anthropic today; every other route resolves to `None` rather than sending a parameter `drop_params` would silently discard. A window that cannot express the ratio above the documented 50,000-token floor is left unarmed rather than clamped to a trigger that can never fire. `chat_native_compaction_enabled` disables it without touching Lumen's own compaction. Returned `compaction` blocks are carried on every later assistant turn of the run, including replayed turns, because a dropped block makes the provider re-compact and re-bill the same prefix; blocks are bounded and re-validated before they are sent back. On the Anthropic passthrough surface the per-iteration `usage.iterations` breakdown now drives billing, since the top-level counters exclude the compaction iteration entirely. Compaction blocks are carried within a run, not across conversation turns — cross-turn continuity remains Lumen's encrypted summary checkpoint. This adds no service, database schema or ownership boundary.

The stateless compatibility proxies (`/v1/messages`, `/v1/responses`, and the Claude gateway) carry no durable run, so Lumen's own fence never sees them and the provider's compaction is the only thing between a long client session and a hard context-length error. `complete_anthropic` and `complete_responses` therefore supply a resolved `context_management` value when — and only when — the caller sent none; a caller that sent its own configuration keeps it untouched, because overriding it would silently change a compatibility client's contract. The two protocols share neither a wire shape nor a floor: Anthropic takes `{"edits": [...]}` with a 50,000-token minimum while the Responses API takes `[{"type": "compaction", "compact_threshold": N}]` with a 1,000-token minimum, so they are resolved separately instead of being translated at the transport. `chat_native_compaction_passthrough_enabled` gates the proxies independently of the chat path because their blast radius differs: a proxy client that does not replay the compaction block pays for a fresh compaction each turn rather than reusing the previous one.

Existing migration013 already provides nullable `ChatApiKey.expires_at`; ordinary issuance now accepts a future timezone-aware timestamp and stores UTC expiry, scopes and owner credit ceilings in one transaction, without new expiry DDL. Null-expiry keys retain their prior lifetime. Fresh authenticated `issuance-policy` exposes the current owner scope ceiling/capability map and quota; `native:keys:*` route actions are not issuable. Actual key verification and new provider/tool I/O continue to recheck active/revoke/expiry and current authority; committed checkpoints remain recoverable. Old/new writer-schema and rolling operation against production snapshots are unqualified, so schema-first coordinated API/worker cutover is required.
- **Redis cache/queue/rate-limit roles**: cache와 run wakeup은 유실되어도 MariaDB 정합성을 바꾸지 않는다. Run wakeup은 class/pool별 hint key이며 worker는 매 loop에서 filtered DB polling을 수행한다. Legacy device brute-force/poll limiter와 realtime 60초 one-use WS ticket는 보안 경계이므로 Redis 장애 시 해당 operation만 fail-closed 503이다. Realtime run은 API socket이 직접 lease를 claim하므로 worker queued polling과 hint에서 제외된다.
- **PostgreSQL boundary**: configured encrypted LangGraph checkpointer는 protocol v2 admission prerequisite이며, `CHAT_MEMORY_PGVECTOR_URL`은 선택 semantic-memory index다. PostgreSQL은 MariaDB run/event/catalog의 대체 정본이 아니다. semantic ranking과 recency prompt hydration도 별도 경로다.
- **Other stores**: configured S3는 service-owned asset object store이고 finite image/TTS/STT media와 Batch Files에는 scanner와 함께 필수다. Batch 입력 JSONL은 업로드 시 scan하고, Lumen이 생성한 `batch_output`은 scan하지 않는다. Batch file은 기존 bucket/encryption policy의 private object이며 metadata/pin/TTL은 `chat_batch_files`가 정본이다. Realtime audio는 S3에 기록하지 않는다. Asset metadata/ownership은 MariaDB가 보유한다. ClamAV/sandbox/MCP는 해당 기능의 외부 boundary다.
- **Internal sandbox boundary**: sandbox의 per-call SQLite journal은 같은 resource의 idempotent local result만 보존하고 LangGraph checkpoint/Redis와 마찬가지로 Lumen의 run/event 정본을 대체하지 않는다. Operator cloud credential과 dispatch key는 controller 전용; worker에는 발급된 client identity만, sandbox에는 해당 resource/run/generation의 파생 key만 들어간다. Public custom HTTP/MCP SSRF restriction은 내부 private transport에 적용되지 않으며 서로 공유하지 않는다.
- **Organization usage windows**: OpenAI/Anthropic 조회는 UTC 월 시작과 현재 주 월요일 중 이른 시각부터 가져온 뒤 일·주·월로 따로 집계한다. 월초에도 전월에 속한 이번 주 사용량을 누락하지 않으며 31개 daily bucket 범위를 유지한다. Route·credential·schema 경계는 변경하지 않는다.
- **Package dependency boundary**: root `lumen` distribution has no base runtime dependency and ships Kolla role files as wheel shared data. Service code, service CLI, and root tests require the explicit `service` extra; development adds `dev`. Kolla-Ansible remains an operator-owned dependency, not a Lumen package dependency.
- **Media accounting/privacy**: 기존 `media_pricing` JSON의 explicit basis와 frozen text/modality rates가 정본이다. Text residual과 image/audio cache split을 중복 청구하지 않으며 optional modality 가격만으로 text-only 호출에 split을 요구하지 않는다. Image/audio worker와 API-owned realtime은 `reserved|unknown` hold를 wallet lock 아래 한도에 포함하고 확정 usage/hold를 같은 transaction에서 정산한다. Provider 상세 usage가 없거나 attribution이 불명확하면 추정·자동 release·재호출하지 않는다. Realtime raw PCM/transcript는 MariaDB/S3에 저장하지 않는다.
- **Priced chat rounds**: configured modality rates는 native/compat admission에서 실제 content part만 보고 preflight하고 provider I/O 전에 freeze한다. Native graph는 provider round·replay마다 required split을 검증한다. Compaction 뒤 text-only round의 알려진 media 부재는 합산에서 0으로 기여하되 checkpoint는 원래 reported usage를 보존한다; 요청한 media의 누락 split을 text fallback으로 바꾸지 않는다. Child call bound와 summary ledger도 같은 frozen modality 최대율/실제 구성요소를 사용한다.

- **API contracts**: native `/v1`은 run descriptor, UUID idempotency, active-path cursor, owner-scoped run/event, replay cursor와 terminal event를 계약으로 한다. Text compat의 OpenAI Chat Completions/Responses와 Anthropic Messages/count_tokens는 stateless지만 image/audio/realtime compat는 별도 durable media run/usage를 생성한다. Discovery의 `clients.claude_code`는 ordinary-key direct Anthropic base를 가리킨다. Legacy Lumen device surface는 custom OAuth grant와 24시간 fixed-scope credential이며 current Claude Apps Gateway compatibility를 주장하지 않는다. discovery/API contract version은 `1.0.0`; published root package `0.6.8`와 SDK `0.2.1`은 별개 release value다.
- **SDK transports**: `lumen_sdk.Client`와 OpenStack SDK `Proxy`는 opaque history cursor를 변환하지 않고 같은 native page contract를 전달한다. 이 둘은 Lumen API transport이며 provider credential transport가 아니다.
- **Protocol invariant**: accepted durable run에는 admission snapshot, pricing/provenance, selected extension/config fingerprint가 있어야 하며 worker가 mutable configuration을 재검증한다. `model="lumen"` bridge는 tools/memory가 없는 text-only 입력만 accepted한다. Compat provider request는 Lumen conversation/active-path에 저장되지 않는다.
- **Release snapshot compatibility**: Migration 020의 기존 text model `model_kind=text`·`media_pricing=NULL`은 v0.3.1의 route HMAC 직렬화에 추가하지 않는다. 정지 시 남은 queued text run은 설정이 실제로 바뀌지 않았다면 기존 frozen hash로 재개하며, 이미지·오디오·realtime route는 kind와 media 가격을 hash에 포함해 변경을 차단한다. 고정된 v0.3.1 HMAC/실제 ORM 조회 회귀가 이 경계를 검증한다.
- **Provider catalog identity/order**: migration 021이 editable `api_provider`와 provider/model `sort_order`를 추가한다. 기존 selector는 transport에서 backfill하며 같은 model/selector의 중복을 rank로 해소하지 않는다. Public API는 selector, credential·reasoning·media·LiteLLM 실행은 `provider_type`, native/durable 선택은 stable provider/model ID를 사용한다. OpenAI Realtime/Gemini Live compat WebSocket은 selector를 받지 않고 wire가 고정한 `provider_type`만 `admit_realtime_session(provider_type=...)`과 `resolve_api_model(provider_type=...)`에 제약으로 전달한다. Catalog는 provider rank·provider ID·model rank·model ID 순이고 selector/rank는 frozen HMAC에 들어가지 않는다. Rank-only model PATCH는 legacy manual/media 가격 version으로 쓰는 `updated_at`을 유지해 queue snapshot을 무효화하지 않는다. 기존 route locks·active-run mutation fence·DB/credential 소유권은 유지한다.
- **Atomic provider model reorder**: 관리자 `POST /v1/admin/models/reorder`는 `{provider_id, expected_model_ids, model_ids}`의 strict positive unique bounded ID 목록을 받는다. Repository가 기존 `_lock_mutable_route`로 provider→전체 model ID 순서 잠금 및 provider 전체 active-run fence를 획득하고, 모든 종류·비활성 모델을 포함한 현재 `(sort_order,id)` 순서를 expected와 대조한다. Stale/membership/active-run 충돌은 409이며 변경 없이 rollback한다. 단일 transaction에서 바뀐 rank만 `0..N-1`로 쓰고 `updated_at`을 명시 보존해 legacy manual/media 가격 version 및 frozen HMAC을 유지한다. Provider/config/가격/flag는 변경하지 않는다. 성공은 no-store 204, provider 부재는 404; migration/dependency 변경은 없다. 실제 HTTP+SQLite 영속 회귀는 test-defined이며 이번 작업에서는 실행하지 않았다.
- **0.3.1 integration boundary**: `origin/dev`의 title/admission/operator/graph reasoning 수정과 기존 subscription sampling·operations 변경을 별도 worktree에서 통합했다. Legacy Perplexity Sonar의 정확한 bundled 가격 키를 synthetic Agent 중복 접두보다 우선해 서로 다른 tariff를 유지한다. Managed runtime guest 인증서의 Authority Key Identifier는 controller CA의 Subject Key Identifier가 있으면 그 값을 사용하고, 없으면 CA 공개키에서 유도한다. 기존 CA material·소유권은 변경하지 않는다. 서비스·schema·dependency·저장소 소유권 변경은 없으며 root/runtime/lock 및 packaged Kolla image default만 patch version으로 맞춘다. 기존 discovery는 변경하지 않았다. 0.3.1 candidate에서 contract 1,369건, SDK 125건, 실제 MariaDB/Redis integration 40건, local Compose fake-provider system 9건, Ruff와 wheel build, API/worker/controller/sandbox linux/amd64·linux/arm64 이미지 build 및 각 이미지의 offline import/platform smoke를 통과했다. `v0.3.1` package/image workflows와 네 tag image의 linux/amd64·linux/arm64 manifest/OCI revision은 게시 후 확인했다. live Anthropic/OpenAI provider·production rollout은 아직 검증하지 않았다.

### Provider model onboarding

관리자 discovery는 Anthropic `x-api-key`/`anthropic-version` + `after_id`, Gemini `x-goog-api-key` + `pageToken`, OpenAI-compatible Bearer `/models`로 계정별 후보를 조회한다. 기존 Perplexity router·custom base와 subscription namespace를 보존한다. HTTP client는 redirects/environment proxy를 사용하지 않고 전체 20초·25페이지·2,000 unique 모델·5MB streamed identity response로 제한한다. 정상 empty는 complete API 결과다. 오류나 중간 페이지 실패·한도 초과는 모델 목록 전체를 폐기하고 safe error로 반환하며 static fallback을 하지 않는다. Static 참고 목록은 live 미지원 provider/auth에만 제공한다.

`available-models`는 no-store와 `provider_id`, `fetched_at`, `source`, `live_status`, `complete`, `error`, `models`, `candidates`를 반환한다. Upstream 401/403은 caller session 오류와 구별되는 HTTP 200 structured discovery error다. 후보의 exact opaque ID·표시명·generation methods·token limits는 등록/가격/고급 기능/실제 추론 증거가 아니다. 신규 ID는 기존 CRUD와 request-time DB route를 사용하며 native admission은 가격 쌍과 별도 feature gate를 검사한다. LiteLLM 계산기가 unknown ID에 0을 반환해도 exact catalog entry의 명시 단가 없이는 free 가격으로 인정하지 않는다. 명시적 0 USD와 미확인 `null`을 구분한다.

`OPENAI_API_KEY`/`GEMINI_API_KEY`가 bootstrap process에 있으면 공식 direct `openai`/`gemini` provider를 자동 등록한다. DB는 key 값이 아닌 `api_key_env` 변수 이름만 갖는다. Existing DB key, admin env binding, custom base, margin, active flag는 bootstrap이 바꾸지 않으며 빈 키를 새 provider로 등록하지 않는다. `LUMEN_BOOTSTRAP_MODELS_JSON`은 관리자가 지원 모델의 단위 가격을 명시할 때만 새 model을 만든다. Media는 kind/variant/초당·분당 rate의 형식과 지원 transport를 검증하지만 공식 제공사 가격의 정확성까지 확인하지는 않는다. 키만으로 media capability·가격·모델을 생성하지 않으며 로컬 기본 text 모델은 별도 seed한다. 이미지/음성/Live 실증은 별도다.

## Deployment and operations

로컬 Compose(`docker-compose.yml`)는 MariaDB, Redis, migration/backfill, idempotent `seed-local`(공통 env provider bootstrap + text 모델 + scoped key), API, worker, opt-in connection helper와 localhost Console을 분리한다. API 기본은 `127.0.0.1:8012`다. `OPENAI_API_KEY`/`GEMINI_API_KEY`는 seed/API/worker에만 전달되고 `.env`는 Git과 Docker build context에서 제외한다. Provider key 없이 stack은 기동해도 completion은 실행되지 않는다. `lumen-migrate --apply`가 기존 projection/Gateway/cache/media migrations를 완료한 뒤 bootstrap이 실행되고 API/worker가 시작된다. Gateway local base는 loopback HTTP를 허용하지만 model/provider route가 없으면 inference는 503이다.

Migration 012의 active-path table은 기존 FK parent와 같은 database collation을 상속하도록 explicit charset/collation을 지정하지 않는다. MariaDB DDL autocommit 뒤 재실행해도 안전하도록 table, column, index 생성은 `IF NOT EXISTS`를 사용하며 integration datastore는 `utf8mb4_unicode_ci` database에서 이 계약을 검증한다.

Media migration의 역사적 identity 변경은 `lumen/scripts/migrate.py`가 좁게 처리한다. Pending `020-media-model-registry`에만 byte-identical `019-media-model-registry`의 파일명·고정 SHA-256과 기존 `model_kind`의 타입/기본값/NOT NULL 및 nullable `media_pricing` JSON 제약을 확인하고, 기존 ledger를 유지한 채 canonical row만 기록한다. Fresh DB는 원래 SQL을 실행하며 dry-run은 기록하지 않고 불일치는 fail-closed다. Schema·service ownership·immutable SQL·기존 checksum 계약은 변경하지 않는다. 경계와 데이터/이력 보존은 실제 격리 MariaDB의 `tests/integration/test_media_registry_migration.py`에서 검증한다; 운영 DB rollout 증거는 별도다.

Service 이미지는 root `service` extra의 workspace plugin distributions와 editable source 경로를 함께 보존한다. `docker/Dockerfile`은 workspace manifests를 먼저 복사하고 `uv sync --locked`로 manifest/lock 불일치를 build 단계에서 거부한다. 최종 API/worker/controller 공통 runtime은 `packages/lumen-plugin-api`와 `plugins/`를 포함하고 non-root 사용자로 실제 `python -m lumen.scripts.migrate --help`를 실행해 import 누락을 검출한다. 이 검사는 DB에 연결하거나 migration을 적용하지 않는다. Sandbox는 이 trusted runtime과 별도 stage이며 service workspace에 포함하지 않는다.

Kolla role은 API/worker를 별도 host-network container로 실행하고 MariaDB/Valkey, Keystone, encryption key, PostgreSQL mode와 `claude_gateway_base_url/model/provider`, Afterglow `frontend_base_url`을 주입한다. Vault-protected inventory `lumen_openai_api_key`, `lumen_gemini_api_key`, optional `lumen_bootstrap_models_json`은 migration 뒤 no_log one-shot CLI와 API/worker env에만 전달된다. Non-loopback Gateway base는 HTTPS와 exact `/v1/claude-gateway` path가 필수다. `deploy`, `upgrade`, `reconfigure` bootstrap은 migration/backfill→provider registration을 API/worker start 전에 실행한다. 현재 source-build pin `c561a155...`는 CLI보다 오래되었으므로 변경된 source/image로 operator가 pin을 갱신하기 전 Kolla 배포를 완료했다고 주장하지 않는다.

`GET /v1/health`와 Kolla healthcheck는 process HTTP response만 확인한다. Migration checksum/projection integrity, DB/Redis, worker, Gateway device login, provider inference readiness는 별도 검증한다. 운영 장애 시 journal, lease, provider snapshot, migration ledger/checksum, unready history count와 Gateway OAuth safe code를 함께 확인한다. Backup은 active-path/device/API-key metadata를 포함한 MariaDB, configured PostgreSQL, S3와 encryption key recovery를 일관되게 계획한다.

Cache teardown은 pinned Redis 5.0.0의 async `close()`를 사용해 소유 pool을 닫고 client 참조를 비운다. `tests/test_cache.py`의 실제 client API 회귀와 0.6.2 준비 당시 contract gate(service1,676·SDK125·Ruff)가 통과했다. 별도 Redis7에 연결한 canonical API image의 native arm64·emulated amd64 실행에서 서버 `CLIENT LIST`로 원래·재생성 TCP connection의 제거, 참조 초기화와 반복 종료를 확인했다. 이 수정은 published `v0.6.2`에 포함되며 API shutdown의 `aclose()` AttributeError에만 해당한다. DB readiness/driver closed-transport 복구는 별도 plugin 경계다.

Database pool pre-ping은 `lumen-database-mariadb` 0.1.1이 소유한다. aiomysql은 pool에서 쉬는 동안 닫힌 socket에 대해 uvloop의 `RuntimeError`(`TCPTransport closed=True … handler is closed`)를 DBAPI 예외로 바꾸지 않으므로, plugin은 이 정확한 signature만 SQLAlchemy pre-ping disconnect로 보고해 pooled connection을 새로 checkout한다. 다른 ping 오류는 그대로 전파되고 host의 availability circuit와 오류 분류는 바뀌지 않는다. 실제 MariaDB/aiomysql/uvloop의 `tests/integration/test_database_pool_recovery.py`는 수정 전 C2와 같은 readiness false를 재현하고 수정 후 갱신된 connection과 unrelated 오류 비은폐를 확인한다. 폐기되는 dead socket의 terminate traceback은 한 번 기록될 수 있다. 기본 allowlist는 database plugin 0.1.1을 승인하며 explicit allowlist는 image와 함께 갱신해야 한다. 상위 socket 종료 원인과 운영 rollout은 별도 증거다.

Published stable `v0.6.2`는 0.6.1의 Redis5·database plugin0.1.1 recovery를 포함한다. 당시 frozen contract(service1,676·SDK125·Ruff), plugin conformance88(1 skip), Linux sandbox14(7 privileged skip), Kolla asset15, real MariaDB/Redis integration107, canonical process-system9와 다중 architecture candidate build가 기록되어 있다. 이 역사적 결과를 0.6.3 통합 tree의 fresh gate로 사용하지 않는다. 0.6.3은 migration 022–025 전에 old API/worker/controller writers와 guest admission을 중지하고 stopped-writer backup을 확보해야 하며 mixed-version rolling cutover는 지원하지 않는다. Batch와 managed runtime은 기본 비활성이며 실제 Nova/Octavia/qcow2/provider 활성화는 별도 운영자 수용 gate다.

## Security boundaries

- **Principal**: Keystone token, scoped ordinary API key와 expiring legacy-device API key를 `Principal`로 정규화하고 current service authority를 검증한다. 여러 credential은 400이지만 동일 API key의 `X-API-Key` + Bearer 중복은 허용한다. Key는 project에 고정되고 verified system owner도 key를 global admin으로 만들지 않는다. Custom gateway는 credential kind와 fixed scope를 추가 검사한다. Key/admin management와 Gateway approval은 Keystone-only; 다른 native management는 service editor/destructive action과 ownership을 검사한다.
- **Authentication I/O scheduling**: async Keystone dependency는 동기 validation을 bounded Starlette thread pool에서 기다린다. Token rescope/target project/admin 판정은 유지하며 cache/fail-open을 추가하지 않는다.
- **Target project**: Keystone connection project와 logical target project를 분리하며 다른 target은 검증된 system admin만 지정할 수 있다. Gateway approval은 현재 authenticated user/project에 grant를 묶는다.
- **Secrets**: encryption key는 64 hex이며 domain separation으로 chat/provider/billing/extension content를 분리한다. Ordinary/Gateway API key와 device/user code는 hash만 저장하고 plaintext credential은 successful issuance response에서 한 번만 노출한다. Raw credential/provider/MCP/Git/S3/tool secret은 log/journal/response에 기록하지 않는다.
- **Kolla managed-runtime identity**: controller만 root-owned 서명 키·CA private key를 읽기 위해 컨테이너 root로 기동하며 Docker socket을 받지 않는다. Stock worker에는 별도 제한된 디렉터리의 public CA·client cert/key 세 파일만 group-readable read-only로 마운트하고, 동일한 container TLS 경로에서 operator key나 CA private key를 노출하지 않는다. Precheck가 파일 위치·소유권·모드·허용된 세 파일만 검증하며 Kolla TOML의 runtime JSON은 문자열로 escape한 뒤 설정 loader가 typed object로 복원한다. Source mode는 controller target도 빌드한다. Compose의 수동 controller profile은 격리/cloud acceptance가 아니다.
- **Network**: custom HTTP/MCP 경계의 SSRF/TLS 정책을 유지한다. Gateway public base는 non-loopback HTTPS만 허용하고 host gate를 적용한다. Device issuance/approval rate limiting은 Redis failure를 503으로 거부한다.
- **Execution trust**: immutable snapshot은 request/config와 committed I/O recovery 경계다. Direct/online/Batch/media/realtime/auxiliary 새 provider/tool I/O는 current owner graph와 key revoke/expiry/scope를 검사한다. 이미 provider-start를 commit한 결과 회수 및 완료 checkpoint 정산은 유지하며 재호출하지 않는다. Scope 감소를 snapshot으로 우회하지 않는다. Owned cancel은 primary operation에 한정한다. Custom Gateway fixed key는 tools scope가 없으므로 client tool schema도 403이다; ordinary scoped API가 별도 연동 경로다.
- **Console**: local Console SQLite는 local password hash/session hash만 저장하고 Lumen API key/Keystone token을 저장하지 않는다. seed volume과 one-shot connection output은 local development secret boundary이며 repository/CI log에 기록하지 않는다.

## Glossary

- **Admission**: 요청 권한·context·provider·extension·pricing을 계산해 immutable run snapshot과 MariaDB transaction을 만드는 단계.
- **BFF**: Afterglow Backend-for-Frontend. Lumen 내부 실행을 소유하지 않고 인증된 browser request를 Lumen `/v1`로 forwarding한다.
- **Durable run**: API/SSE 연결과 독립적으로 MariaDB journal, lease, worker execution으로 진행되는 실행 단위.
- **Journal**: `ChatRunEvent` sequence와 terminal state를 포함하는 authoritative run/event 기록.
- **Lease**: 한 worker owner만 run을 갱신하도록 하는 만료 가능한 실행 소유권.
- **Snapshot**: admission 시점 provider/model/feature/extension/context/pricing identity를 freeze한 값.
- **Stateless completion**: provider model ID를 직접 LiteLLM으로 호출하고 HTTP 요청의 응답으로 끝나는 compat 경로.
- **Virtual model `lumen`**: OpenAI compat에서만 제공되는 durable bridge 식별자. text-only native-like worker execution을 뜻한다.
- **MCP**: Model Context Protocol remote server/tool 경계. Lumen은 owner-scoped selection과 Afterglow control-plane authority를 재검증한다.
- **Checkpointer/pgvector**: 각각 protocol-v2 LangGraph state checkpoint와 선택 semantic-memory index를 위한 PostgreSQL 경계.
- **Console**: Afterglow UI가 아닌 local developer/operator tooling. Lumen API 인증·scope·durable admission을 우회하지 않는다.

## Balanced infrastructure controller (test-passed; local parent receipt)

This addendum retains the original narrow `balanced-infrastructure-controller` receipt for `lumen/services/infrastructure/{_coordination,controller,store}.py`, not a claim that those earlier checks reviewed the entire integrated checkout. Its original parent receipt was focused110 passed, disposable MariaDB/Redis integration110 passed/3393 deselected and service contract3159 passed/344 deselected, SDK128 and both gate Ruff scopes passed; repository-wide Ruff retained the HEAD-baseline SIM102 finding. These remain historical snapshot results. The fresh integrated0.6.8 qualification and read-only production ledger baseline above supersede authored-only/unexecuted handoff language, not the unexercised real-cloud, mixed-version or deployment boundaries. The architecture marker now records this documentation/evidence review via the repository checker; it is not a new whole-source security audit. See [testing](docs/testing.md#balanced-infrastructure-controller-acceptance-test-passed) for the original commands and snapshot.

- **Scheduling hints:** `PoolCoordinator` uses a deployment-hashed Redis Cluster hash tag with participant sorted set, eligibility hash and persistent registry key. One Lua snapshot uses Redis `TIME` to purge expired participation and eligibility, elect the lexically first live owner and condition publication on current leadership. Participation lasts 30 seconds; the dispatcher runs at `min(5 seconds, reconcile_interval_seconds)`. `current()` checks do not renew or resurrect expired membership. Registry persistence is not evidence that any owner or SQL lease remains live.
- **Eligible balance:** Registry entries hold SQL pool ID and configured pool digest; members advertise enabled, provider-backed pool name/digest pairs. Exact equality is required. Assignment is deterministic under unchanged membership/registry, scarce-pools-first least load with deterministic hash tie breaks and alternating owner/pool paths so a flexible incumbent can move another pool to give a constrained late join useful work when feasible. With common eligibility, member pool counts differ by at most one. This is per-process pool-count balance, not resource-cost/node-weighted balance, minimum movement or rendezvous-only ownership; no general feasibility-optimal matching claim is made.
- **Registry ownership:** Only the current Redis leader discovers/synchronizes configured SQL pools and publishes the enabled registry. `store.sync_pools(..., leader_check=...)` checks before SQL discovery, after waiting for pool row locks and before transaction commit; a lost check raises `PoolLeaseLost` and rolls back. Publication is separately conditional on the current leader. Redis and SQL are not one atomic fence: an already-started SQL transaction may settle across a subsequent Redis leadership change. SQL owner/fence/expiry and resource generation remain the final cloud-effect authority. Configured cloud-provider preflight still runs per controller process at startup.
- **Independent progress:** Heartbeat/dispatcher launches a separately owned registry task and one owned task per assigned pool, with per-pool reconcile cadence. It never waits for slow SQL discovery, SDK reconciliation or another pool's work. An assigned controller still must claim the pool's SQL lease (30 seconds, renewed every 10 seconds); assignment alone grants no cloud write permission.
- **Handoff and failure:** Current assignment is checked immediately before SDK submission (including the locked `_renewed_effect`) and outbound controller guest drain POST. Assignment loss, expiry or failed Redis reads prevent new cloud/outbound controller guest steps; there is no all-pool SQL-claim fallback. Already submitted effects, sibling coroutines and SDK threads drain and persist their outcomes under existing SQL fencing before owner+fence CAS lease release. Stop joins pool/registry tasks before Redis leave and executor shutdown. A crash waits for Redis participation expiry and SQL lease/row-lock safety before takeover; unknown creates are observed/adopted, not blindly replayed. A late join changes assignments but cannot preempt an active SQL effect. Redis restoration permits heartbeat/recomputed assignment, not bypass of SQL fencing.
- **Unchanged ownership:** API admissions and durable workers already use SQL workload-class/pool assignment and competing run/auxiliary consumers; their Redis wakeup-loss DB-polling fallback remains separate. Node-local HTTP/SSE/WS meters, guest API request handlers and controller bootstrap/identity listener requests stay local/request-owned; they are not elected global roles. This change gates outbound controller actions, not guest request handling.

See [operations](docs/operations.md#balanced-infrastructure-controller-participation-and-handoff) and [testing](docs/testing.md#balanced-infrastructure-controller-acceptance-test-passed) for the local parent receipt, rollout boundaries and executable local acceptance recipes.
