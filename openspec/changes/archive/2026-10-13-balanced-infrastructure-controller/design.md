## Context

Lumen controllers manage configured cloud pools backed by MariaDB resource/operation journals and renewable pool leases. Running identical controllers against all pools causes unnecessary registry work and contention. Accepted API/worker runs already have SQL workload-class/pool assignment and competing consumers, so adding a second queue scheduler would conflict with existing authority. Preserve existing WIP, native engineering boundaries and architecture review marker.

## Goals / Non-Goals

**Goals:** deterministic useful work distribution among exact-compatible controller processes; leader-only registry discovery/sync; Redis-time liveness independent of cloud/SQL latency; SQL-fenced drain-before-release; executable local acceptance with honest evidence.

**Non-Goals:** API/worker queue rewrite, node-local request/guest handler election, per-process provider-preflight election, schema migration, new dependency, cross-store atomic SQL/Redis fence, minimum mapping movement, weighted physical-controller balance, production deployment or real cloud/inference proof.

## Decisions

1. **Service-native Redis participation:** `PoolCoordinator` has deployment-hashed Cluster-compatible participants/eligibility/registry keys. Lua uses Redis `TIME`, atomically purges expired entries, elects the lexical live owner and gates registry publication. Participation is 30 seconds; heartbeat/dispatcher cadence is `min(5, reconcile_interval_seconds)` seconds. `current()` never renews membership. Registry survives participation expiry. Alternative: all replicas discover/claim SQL pools; rejected because it repeats discovery and does not distribute target work.
2. **Exact eligible balanced assignment:** Members advertise enabled provider-backed pool names and configuration digests; registry maps name to SQL ID and digest. `assign_pools` processes scarce pools first, searches alternating owner/pool paths and chooses least load with deterministic path-length/hash/owner tie breaks. It may relocate a flexible incumbent's pool to give a constrained late join useful work. Common eligible sets yield count difference at most one; unchanged inputs yield unchanged mapping. Alternative: rendezvous-only ownership; rejected because one member can retain all useful pools. No minimum-movement/general feasibility-optimal matching guarantee.
3. **Leader-only sync with explicit cross-store limit:** Required keyword `leader_check` is invoked before SQL discovery, after the `FOR UPDATE` wait and before commit; loss raises `PoolLeaseLost` and rolls back. `_sync_registry` publishes only if Redis still identifies the owner as leader. An already-started SQL transaction can settle across a subsequent Redis change; these are boundary checks, not an atomic Redis/SQL fence. Alternative: claim Redis as SQL commit authority; rejected because no atomic cross-store transaction exists. Existing SQL cloud owner/fence/expiry remains final authority.
4. **Independent dispatcher and executions:** `tick()` heartbeats and launches `_registry_task` plus `_pool_tasks`; `_pool_due` enforces each reconcile interval. It does not await registry/cloud execution. Each assigned pool then claims a 30-second SQL lease with 10-second renewal. Alternative: synchronous registry+all-pool loop; rejected because one slow operation could expire participation or starve another pool.
5. **Gate new I/O, settle submitted I/O:** `_check_assignment` reads current membership immediately before every SDK submission, including locked `_renewed_effect`, and outbound guest drain POST. Redis read errors/expiry/reassignment stop new steps without an all-pool fallback. `_joined` and settled SDK execution retain sibling/thread ownership; already-submitted results and unknown outcomes drain/record under SQL fences. `release_pool_lease` clears only matching owner+fence after reconciliation settles. Controller stop drains registry/pool tasks, then leaves Redis, then shuts down its executor. Alternative: cancel tasks/release hints immediately; rejected because cancellation is not thread completion or cloud outcome evidence.

## Risks / Trade-offs

- Redis outage intentionally halts new controller actions, unlike optional durable run wakeups; accepted worker runs still recover by SQL polling. Recovery requires heartbeat and renewed assignment plus SQL authority.
- Late joins can change mapping and wait for SQL drain. Process crash requires participation expiry and safe SQL takeover; no hard failover deadline is claimed. Unknown creates retain observation/adoption/non-replay semantics.
- Per-process pool counts are not resource cost or physical-node balance. A persistent registry can be stale until the next leader sync, and digest-incompatible members must not reconcile it.
- Leadership may change just after a SQL boundary check. Record the limitation rather than advertise an atomic fence; SQL resource/operation fences order actual cloud effects.
- Mixed old/new controller execution, Redis failover persistence characteristics, live Nova/Octavia, guest mTLS and production restore/schema compatibility need separately authorized evidence.
